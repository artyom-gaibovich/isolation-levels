# Ответы: Транзакции и уровни изоляции

---

## 1. Транзакция — это примитив языка или БД?

Транзакция — это примитив **базы данных**. СУБД (PostgreSQL, MySQL и др.) реализует транзакционность на уровне движка хранилища: она управляет журналом (WAL/undo log), блокировками и MVCC.

Язык программирования (Go, Java, Python) лишь предоставляет **API для управления** транзакцией — `BEGIN`, `COMMIT`, `ROLLBACK`. Сам механизм атомарности, изоляции и долговечности живёт целиком в БД.

---

## 2. Можно ли без явного описания транзакции в коде заставить БД выполнять запросы в транзакции?

Да. В большинстве СУБД есть режим **autocommit**:

- Когда autocommit **включён** (по умолчанию в PostgreSQL и MySQL), каждый отдельный SQL-запрос автоматически оборачивается в неявную транзакцию и сразу фиксируется.
- Когда autocommit **выключен** (`SET AUTOCOMMIT = OFF` в MySQL или использование `BEGIN` без явного `COMMIT`), все запросы выполняются в рамках одной открытой транзакции до тех пор, пока не будет вызван `COMMIT` или `ROLLBACK`.

Помимо этого, можно настроить триггеры или использовать средства БД (например, процедуры), внутри которых управление транзакцией происходит без участия приложения.

---

## 3. Можно ли не использовать транзакцию, но добиться той же функциональности?

**Средствами языка:** частично. Можно реализовать логику «компенсирующих операций» (паттерн Saga) — если один шаг упал, вручную откатить уже сделанные шаги обратными запросами. Но это:
- Не атомарно (между шагами другие процессы видят промежуточные данные).
- Ненадёжно (при падении приложения компенсация не выполнится).
- Значительно сложнее в реализации.

**Средствами БД:** можно использовать `SAVEPOINT`-ы, хранимые процедуры или триггеры — но они сами внутри используют механизм транзакций.

**Зачем тогда транзакция?** Потому что она даёт **гарантии ACID** из коробки: атомарность, согласованность, изоляцию и долговечность — без ручной реализации компенсаций. Это надёжнее, проще и корректнее.

---

## 4. Если не использовать транзакции, к чему это может привести?

- **Частичное обновление данных:** если приложение упало в середине нескольких запросов, данные окажутся в несогласованном состоянии.
- **Грязные/фантомные чтения** между конкурирующими запросами.
- **Потерянные обновления:** два процесса читают одно значение, оба его меняют — одно изменение теряется.
- **Нарушение инвариантов БД:** бизнес-правила, требующие атомарного изменения нескольких таблиц, будут нарушены.

Итог: данные станут **непредсказуемо некорректными** при любом сбое или параллельном доступе.

---

## 5. Как часто мы пользуемся функцией отмены (Rollback)?

В production-коде явный `ROLLBACK` используется **реже**, чем кажется. Чаще всего откат происходит **автоматически**:

- При ошибке внутри транзакции в большинстве драйверов.
- При закрытии соединения без `COMMIT`.
- При `defer tx.Rollback()` в Go (стандартный идиоматичный паттерн).

Явный `ROLLBACK` нужен в бизнес-логике, когда мы сами решаем отменить транзакцию при валидационной ошибке (не SQL-ошибке). Например: «если баланс после операции ушёл в минус — откатить».

---

## 6. Насколько сильно транзакция ухудшает производительность?

Транзакция **сама по себе почти не влияет** на производительность при правильном использовании. Накладные расходы:

- Запись в журнал (WAL) — происходит и без явных транзакций (при autocommit тоже пишется WAL).
- Удержание блокировок — чем дольше транзакция открыта, тем больше конкуренция.
- При высоком уровне изоляции (SERIALIZABLE) — возможны дополнительные блокировки и конфликты.

**Что реально снижает производительность:**
- Долгоживущие транзакции (удерживают локи и мешают vacuum в PostgreSQL).
- Высокий уровень изоляции при высоком параллелизме.
- Большое количество мелких транзакций вместо batch-операций.

---

## 7. Как работает Rollback? Он создаёт запросы, отменяющие предыдущие?

`ROLLBACK` **не создаёт обратные запросы**. Механизм зависит от СУБД:

**PostgreSQL (MVCC):** при выполнении запросов в транзакции создаются новые версии строк с указанием транзакции-создателя (`xmin`). При откате транзакция помечается как прерванная (`aborted`). Старые версии строк просто перестают быть видны — физически они остаются до прохода `VACUUM`. Никаких «обратных» запросов нет.

**MySQL InnoDB (undo log):** все изменения сначала пишутся в undo-лог. При откате движок применяет записи из undo-лога в обратном порядке, восстанавливая исходные значения строк.

В обоих случаях это внутренние механизмы БД — не SQL-запросы.

## 8. В чём разница между statement и prepared statement?

**Statement (обычный запрос):**
```go
db.QueryContext(ctx, "SELECT * FROM users WHERE id = " + id)
```
- Каждый раз парсится, планируется и выполняется заново.
- Уязвим для SQL-инъекций при конкатенации.

**Prepared Statement:**
```go
stmt, _ := db.PrepareContext(ctx, "SELECT * FROM users WHERE id = $1")
stmt.QueryContext(ctx, id)
```
- Парсинг и построение плана происходит **один раз** при подготовке.
- Параметры передаются отдельно — нет SQL-инъекций.
- При повторных вызовах с разными параметрами работает быстрее.

**В контексте транзакции:**
Оба работают одинаково с точки зрения транзакционной семантики. Разница: `tx.PrepareContext` создаёт prepared statement, привязанный к данной транзакции — он будет автоматически освобождён при `COMMIT`/`ROLLBACK`. Можно также использовать `tx.StmtContext(stmt)` чтобы «адаптировать» уже существующий prepared statement для работы в транзакции.

**При откате:** не имеет значения, какой тип запроса использовался — все изменения данных откатываются одинаково.

## 9. Что такое ReadOnly? Почему нужна эта опция?

`ReadOnly` — флаг транзакции, указывающий, что она будет только читать данные:

```go
tx, err := db.BeginTx(ctx, &sql.TxOptions{ReadOnly: true})
```

**Зачем нужно:**
1. **Оптимизация в БД:** PostgreSQL может маршрутизировать read-only транзакции на реплику. Также СУБД не создаёт undo-лог для таких транзакций.
2. **Защита от случайных записей:** если внутри транзакции попытаться выполнить `INSERT`/`UPDATE` — получим ошибку.
3. **Документирование намерения:** явно показывает, что транзакция только читает.

**Можно ли реализовать через уровни изоляции?**
Нет, уровни изоляции управляют *видимостью* данных, а не *разрешением* на запись. `READ COMMITTED` с `ReadOnly=false` всё равно позволит писать. Это разные ортогональные настройки.

---

## 10. Сколько уровней изоляции существует? Чем они отличаются?

По стандарту SQL (ANSI/ISO SQL-92) определены **4 уровня изоляции**:

| Уровень | Dirty Read | Non-Repeatable Read | Phantom Read |
|---|---|---|---|
| READ UNCOMMITTED | возможен | возможен | возможен |
| READ COMMITTED | нет | возможен | возможен |
| REPEATABLE READ | нет | нет | возможен |
| SERIALIZABLE | нет | нет | нет |

В PostgreSQL практически нет READ UNCOMMITTED (ведёт себя как READ COMMITTED из-за MVCC). PostgreSQL также добавляет дополнительные аномалии, не описанные в стандарте (Write Skew и др.).

**Почему нельзя использовать один уровень всегда?**

Чем выше уровень изоляции, тем:
- Больше блокировок или конфликтов сериализации.
- Ниже пропускная способность (throughput) при высоком параллелизме.
- Больше вероятность deadlock или retry при SERIALIZABLE.

Для большинства операций READ COMMITTED достаточен и значительно производительнее SERIALIZABLE.

---

## 11. Можно ли сделать транзакцию без изоляции данных?

**READ UNCOMMITTED** — это фактически транзакция без изоляции (можно читать незафиксированные изменения других транзакций). В PostgreSQL этот уровень поддерживается синтаксически, но ведёт себя как READ COMMITTED.

В MySQL InnoDB READ UNCOMMITTED работает по-настоящему и позволяет грязное чтение.

**Влияние на производительность при READ UNCOMMITTED:**
Да, влияние есть, но минимальное. Транзакция всё равно пишет в WAL, удерживает блокировки на запись (write locks остаются), просто снимаются ограничения на чтение. Накладные расходы самого `BEGIN`/`COMMIT` остаются.

---

## 12. Какой уровень изоляции больше всего снижает производительность?

**SERIALIZABLE** — наиболее дорогой уровень.

**Механизм снижения производительности:**

В PostgreSQL используется алгоритм **SSI (Serializable Snapshot Isolation)**:
- Отслеживаются зависимости между транзакциями (rw-конфликты).
- При обнаружении опасных зависимостей одна из транзакций прерывается с ошибкой `ERROR: could not serialize access due to concurrent update`.
- Приложение обязано **повторять транзакцию** при таких ошибках.
- Дополнительные структуры данных в памяти для отслеживания зависимостей.

В MySQL/SQL Server SERIALIZABLE использует **range locks** (блокировки диапазонов), что значительно снижает параллелизм.

## 13. Аномалии транзакций с примерами

### Lost Update (Потерянное обновление)
Две транзакции читают одно значение, обе его изменяют, вторая перезаписывает изменение первой.

```
T1: SELECT balance FROM account WHERE id=1  → 100
T2: SELECT balance FROM account WHERE id=1  → 100
T1: UPDATE account SET balance=150 WHERE id=1  (100+50)
T2: UPDATE account SET balance=80  WHERE id=1  (100-20) ← затирает изменение T1
```
Итог: +50 от T1 потеряно.

### Missing or Double Read (Потерянное или двойное чтение)
Запрос дважды читает одни данные, но между чтениями другая транзакция вставляет или удаляет строку — результат отличается.

```
T1: SELECT COUNT(*) FROM orders  → 10
T2: INSERT INTO orders ...
T1: SELECT COUNT(*) FROM orders  → 11  ← Phantom Read (двойное чтение даёт разный результат)
```

### Dirty Read (Грязное чтение)
Транзакция читает незафиксированные данные другой транзакции.

```
T1: UPDATE account SET balance=0 WHERE id=1
T2: SELECT balance FROM account WHERE id=1  → 0  ← грязное чтение
T1: ROLLBACK  ← данные вернулись к исходному значению
T2 работала с некорректными данными
```

### Non-Repeatable Read (Неповторяющееся чтение)
Транзакция дважды читает одну строку и получает разные значения (другая транзакция успела зафиксировать изменение).

```
T1: SELECT balance FROM account WHERE id=1  → 100
T2: UPDATE account SET balance=200 WHERE id=1; COMMIT
T1: SELECT balance FROM account WHERE id=1  → 200  ← другой результат
```

### Phantom Read (Фантомное чтение)
Транзакция дважды выполняет запрос с условием и получает разное количество строк (другая транзакция вставила/удалила строки, попадающие под условие).

```
T1: SELECT * FROM orders WHERE amount > 1000  → 5 строк
T2: INSERT INTO orders (amount) VALUES (1500); COMMIT
T1: SELECT * FROM orders WHERE amount > 1000  → 6 строк  ← фантом
```

### Write Skew #0 (чтение + запись в разные строки)
Каждая транзакция читает данные, на основе которых принимает решение о записи в *другую* строку. В итоге нарушается инвариант.

```
Инвариант: хотя бы один врач должен быть на дежурстве.
T1: SELECT COUNT(*) FROM doctors WHERE on_call=true → 2
T2: SELECT COUNT(*) FROM doctors WHERE on_call=true → 2
T1: UPDATE doctors SET on_call=false WHERE id=1  (думает: останется 1)
T2: UPDATE doctors SET on_call=false WHERE id=2  (думает: останется 1)
Итог: 0 врачей на дежурстве — инвариант нарушен.
```

### Write Skew #1 (конфликт на пересечении)
Две транзакции читают непересекающиеся диапазоны и пишут в них, нарушая глобальный инвариант.

```
Инвариант: сумма остатков на счетах A и B >= 0.
T1: READ A=50, READ B=50 → пишет A=-100 (думает: A+B=50-100+50=0, норм)
T2: READ A=50, READ B=50 → пишет B=-100 (думает: A+B=50+50-100=0, норм)
Итог: A=-100, B=-100 → сумма=-200, инвариант нарушен.
```

### Write Skew #2 (чтение пустого множества → запись)
Транзакция проверяет отсутствие данных и, убедившись, что их нет, вставляет запись. Обе транзакции делают это одновременно — получается дублирование.

```
Инвариант: username уникален в таблице без UNIQUE constraint.
T1: SELECT * FROM users WHERE name='alice' → пусто
T2: SELECT * FROM users WHERE name='alice' → пусто
T1: INSERT INTO users (name) VALUES ('alice')
T2: INSERT INTO users (name) VALUES ('alice')
Итог: две записи с одинаковым именем.
```
(В реальности решается UNIQUE constraint, но Write Skew #2 описывает класс проблем, когда проверки недостаточно.)

### Read Skew (аномалия чтения)
Транзакция читает связанные данные из нескольких мест, но между чтениями другая транзакция успела их изменить — данные оказываются несогласованными между собой.

```
Инвариант: A + B = 100. Изначально A=50, B=50.
T2: UPDATE ... SET A=0, B=100; COMMIT
T1: READ A → 50  (до изменения T2)
T1: READ B → 100 (после изменения T2)
T1 видит A=50, B=100 → сумма=150, несогласованная картина.
```

## 14. Каждая операция в транзакции отправляется отдельным запросом по сети?

**Да, по умолчанию** — каждая операция (`db.QueryContext`, `db.ExecContext` внутри транзакции) отправляется отдельным сетевым запросом к БД. Транзакция не буферизует запросы.

**Два режима в Go:**

**Режим 1 — каждая операция отдельным запросом (стандартное поведение):**
```go
tx, _ := db.BeginTx(ctx, nil)
tx.ExecContext(ctx, "INSERT INTO a VALUES ($1)", 1)  // сетевой запрос
tx.ExecContext(ctx, "INSERT INTO b VALUES ($1)", 2)  // сетевой запрос
tx.Commit()                                           // сетевой запрос
```

**Режим 2 — всё одним запросом через многострочный SQL или batch:**
```go
tx, _ := db.BeginTx(ctx, nil)
tx.ExecContext(ctx, `
    INSERT INTO a VALUES (1);
    INSERT INTO b VALUES (2);
`)  // один сетевой запрос (если драйвер поддерживает multi-statement)
tx.Commit()
```

Либо использовать `COPY` (для PostgreSQL), `pgx` batch API, или передать всё как одну хранимую процедуру.

## 15. 5 огромных операций, каждая зависит от предыдущей, между ними бизнес-логика

**Верно ли, что выполняем каждую операцию отдельным запросом?**

Да. Если между операциями есть бизнес-логика в Go (обработка результата предыдущего запроса), то каждую операцию придётся отправлять отдельным запросом — иначе нельзя получить результат и принять решение.

```go
tx, _ := db.BeginTx(ctx, nil)

rows, _ := tx.QueryContext(ctx, "UPDATE table1 ...")  // запрос 1
result1 := parseRows(rows)                            // бизнес-логика в Go

if result1.NeedsUpdate {
    tx.ExecContext(ctx, "UPDATE table2 WHERE id=$1", result1.ID)  // запрос 2
}
// ...
tx.Commit()
```

**Сможем ли откатить при разрыве сети?**

Нет. Если произошёл разрыв сети между запросами 3 и 4:
- Запросы 1-3 уже выполнены на стороне БД, но **не зафиксированы** (транзакция не закрыта).
- PostgreSQL сам обнаружит обрыв соединения и **автоматически откатит** незафиксированную транзакцию.
- Данные вернутся в исходное состояние.

Это одна из ключевых гарантий транзакций: если не было `COMMIT` — изменения не сохранятся.

## 16. Можно ли делать вложенные транзакции?

**Классических вложенных транзакций** (как в некоторых языках) в SQL нет. Но есть **SAVEPOINT** — механизм частичного отката внутри транзакции:

```sql
BEGIN;
  INSERT INTO a VALUES (1);
  SAVEPOINT sp1;
  INSERT INTO b VALUES (2);
  ROLLBACK TO SAVEPOINT sp1;  -- откатывает только INSERT INTO b
  INSERT INTO c VALUES (3);
COMMIT;  -- зафиксирует INSERT INTO a и INSERT INTO c
```

В Go через `database/sql`:
```go
tx, _ := db.BeginTx(ctx, nil)
tx.ExecContext(ctx, "INSERT INTO a VALUES (1)")
tx.ExecContext(ctx, "SAVEPOINT sp1")
tx.ExecContext(ctx, "INSERT INTO b VALUES (2)")
tx.ExecContext(ctx, "ROLLBACK TO SAVEPOINT sp1")
tx.ExecContext(ctx, "INSERT INTO c VALUES (3)")
tx.Commit()
```

**Зачем нужны вложенные транзакции (savepoints)?**
- Откатить только часть работы, не разрушая всю транзакцию.
- Полезно при вызове хранимых процедур или при обработке ошибок в цикле, когда хочется пропустить конкретную запись, но продолжить работу с остальными.

**Почему нельзя использовать отдельные независимые транзакции?**
Потому что независимые транзакции фиксируются независимо. Нельзя атомарно откатить набор отдельных транзакций.

---

## 17. Можно ли настроить внешнюю транзакцию так, чтобы она откатывалась при падении любой вложенной?

Да — это поведение по умолчанию, если вложенные операции выполняются в рамках одной транзакции с savepoints. При ошибке мы откатываем до начала (`ROLLBACK`, не `ROLLBACK TO SAVEPOINT`).

**Зачем тогда вложенные транзакции (savepoints)?**
Они нужны именно тогда, когда мы хотим **НЕ** откатывать всё при ошибке в одном шаге, а только этот шаг. Типичный пример: батч-обработка, где нужно сохранить успешные записи и пропустить ошибочные.

Если же нужна семантика «всё или ничего», достаточно одной транзакции без savepoints.

## 18. Три приложения, каждое пишет в БД — как сделать единую транзакцию?

**Если все три приложения пишут в одну БД:**

Использовать **распределённые транзакции** нельзя напрямую через три разных сервиса, если каждый сам управляет соединением. Варианты:

1. **Одно приложение управляет транзакцией:** первое приложение открывает транзакцию, передаёт `transaction ID` другим приложениям (например, через заголовок HTTP), и те работают в этой же транзакции. Нестандартно, сложно в реализации.

2. **Паттерн Saga:** каждое приложение имеет свою транзакцию, но при сбое выполняются компенсирующие операции (обратные действия). Нет ACID-гарантий, но обеспечивает eventual consistency.

3. **Оркестратор:** отдельный сервис управляет последовательностью шагов и координирует откат при ошибке.

**Если каждое приложение пишет в разные БД:**

Нужен **двухфазный коммит (2PC, Two-Phase Commit)**:
- Фаза 1 (Prepare): координатор просит все БД подготовиться к фиксации.
- Фаза 2 (Commit/Rollback): если все готовы — фиксация, иначе откат.

В Go для PostgreSQL есть поддержка `PREPARE TRANSACTION` / `COMMIT PREPARED`. Но 2PC редко применяется в микросервисах из-за сложности и низкой производительности.

**Если разные схемы одной БД:**

Одна транзакция работает с несколькими схемами в рамках одного соединения — это штатная ситуация, никаких дополнительных механизмов не нужно:
```sql
BEGIN;
  INSERT INTO schema_a.table1 VALUES (1);
  INSERT INTO schema_b.table2 VALUES (2);
COMMIT;
```

---

## 20. Будет ли работать транзакция при операциях в разных схемах? А при linked server?

**Разные схемы одной БД:** Да, транзакция работает без ограничений. Схемы — это лишь пространства имён внутри одной БД, одно соединение может работать с ними одновременно.

```sql
BEGIN;
  UPDATE schema_billing.accounts SET balance = balance - 100 WHERE id = 1;
  UPDATE schema_orders.orders SET status = 'paid' WHERE id = 42;
COMMIT;  -- атомарно
```

**Linked Server (SQL Server):** Транзакции через linked server работают, но требуют **распределённого координатора транзакций (DTC)**. В SQL Server это Microsoft DTC. Риски:
- Значительно снижает производительность.
- Требует специальной настройки сети и сервисов.
- Слабо поддерживается в облачных окружениях.

В PostgreSQL аналог — `dblink` или `postgres_fdw`, но полноценный 2PC через них не поддерживается автоматически.

## 21. На основании чего выбирать уровень изоляции?

Выбор основывается на **балансе между корректностью и производительностью**:

1. **Какие аномалии допустимы для данного запроса?**
   - Отчёт, где небольшое расхождение некритично → `READ COMMITTED`.
   - Финансовая операция → `REPEATABLE READ` или `SERIALIZABLE`.

2. **Какой уровень параллелизма ожидается?**
   - Высокая нагрузка → предпочтительны более низкие уровни.

3. **Есть ли Write Skew в логике?**
   - Если да → нужен `SERIALIZABLE`.

**Рекомендация по умолчанию для PostgreSQL:** `READ COMMITTED` для большинства операций, `REPEATABLE READ` или `SERIALIZABLE` для критичных финансовых/инвентарных операций.

**Можно ли в одной транзакции иметь вложенные транзакции с разным уровнем изоляции?**

Нет. Уровень изоляции задаётся для всей транзакции при её начале и не меняется для вложенных savepoints. Savepoints не имеют своего уровня изоляции.

---

## 22. Какой уровень изоляции в PostgreSQL по умолчанию?

**READ COMMITTED** — уровень по умолчанию в PostgreSQL.

**Можно ли изменить в настройках БД?**

Да:
```sql
-- Глобально для кластера (postgresql.conf):
default_transaction_isolation = 'repeatable read'

-- Для текущей сессии:
SET default_transaction_isolation = 'serializable';

-- Для конкретной роли:
ALTER ROLE myuser SET default_transaction_isolation = 'repeatable read';
```

**Если в Go указан один уровень, а в БД другой — какой победит?**

Уровень, указанный в Go (в запросе `BEGIN TRANSACTION ISOLATION LEVEL ...`), **всегда перекрывает** значение по умолчанию из конфигурации БД. Конфигурация БД — это лишь дефолт при отсутствии явного указания.

```go
// Go явно указывает уровень → будет использован именно он
tx, _ := db.BeginTx(ctx, &sql.TxOptions{
    Isolation: sql.LevelSerializable,
})
```

## 23. Можно ли в БД настроить уровень изоляции так, чтобы он использовался несмотря на запрос приложения?

Стандартными средствами PostgreSQL — **нет**. `SET default_transaction_isolation` задаёт дефолт, но приложение может его переопределить.

Возможные обходные пути:
1. **Функция-триггер или правило** — нестандартно, сложно.
2. **Промежуточный прокси** (PgBouncer, pgpool) с перехватом и модификацией команд — экзотично.
3. **Ограничение прав:** запретить роли выполнять `SET TRANSACTION ISOLATION LEVEL` (но это не прямой способ принудить к конкретному уровню).

На практике это не распространённая задача — обычно управление уровнем изоляции остаётся на стороне приложения.

## 24. Можно ли в БД отключить транзакции в принципе?

**В PostgreSQL — нет.** Транзакционность встроена в ядро движка и не может быть отключена. Даже при autocommit каждый запрос выполняется в неявной транзакции.

**Возникнет ли ошибка, если приложение отправит BEGIN?**

Нет, не возникнет. `BEGIN` — это валидная SQL-команда, и PostgreSQL её примет. Нет режима, в котором БД отвергала бы транзакционные команды.

Некоторые NoSQL-базы (Redis, Cassandra в базовом режиме) изначально не поддерживают транзакции или поддерживают ограниченно, но это другая категория хранилищ.

## 25. Можно ли по логам БД понять, что запрос выполнялся в транзакции?

**Да, можно** при соответствующей настройке логирования.

**В PostgreSQL:**

```ini
# postgresql.conf
log_min_duration_statement = 0  # логировать все запросы
log_line_prefix = '%m [%p] %q%u@%d '
```

В логах появятся:
```
LOG:  statement: BEGIN
LOG:  statement: UPDATE accounts SET balance = 100 WHERE id = 1
LOG:  statement: COMMIT
```

Также можно включить:
```ini
log_transaction_sample_rate = 1.0  # логировать все транзакции (PostgreSQL 12+)
```

**`pg_stat_activity`** — показывает текущие транзакции в реальном времени:
```sql
SELECT pid, state, xact_start, query 
FROM pg_stat_activity 
WHERE xact_start IS NOT NULL;
```

**`pg_locks`** — показывает блокировки, удерживаемые транзакциями.

По `transaction_id` (видному в `pg_stat_activity`) можно отследить все запросы одной транзакции.

## 26. Можно ли отключить транзакции только для одной таблицы?

**В PostgreSQL — нет.** Транзакционность не настраивается на уровне отдельной таблицы.

Исключение — **UNLOGGED таблицы:**
```sql
CREATE UNLOGGED TABLE fast_cache (id int, data text);
```
Unlogged таблицы не пишут в WAL, поэтому:
- Работают быстрее (нет fsync).
- **При сбое БД данные теряются** (не восстанавливаются из WAL).
- Транзакции на них формально работают, но без гарантии долговечности (Durability из ACID).

**Что происходит, если транзакция использует несколько таблиц, одна из которых UNLOGGED?**

Транзакция выполняется и фиксируется, но:
- Изменения в обычных таблицах защищены WAL и восстанавливаются после сбоя.
- Изменения в UNLOGGED таблицах при сбое теряются.
- В итоге данные в разных таблицах могут оказаться несогласованными после краша и восстановления.

Поэтому UNLOGGED таблицы подходят только для кешей и временных данных, потеря которых допустима.
