# Lost Update (Потерянное обновление)

## Что такое Lost Update?

**Lost Update** — один из феноменов параллельного выполнения транзакций. Также известен как **Write-Write Conflict**.

Феномен не ограничивается транзакциями в БД — он встречается также:
- При взаимодействии с сервером через **веб** (параллельные HTTP-запросы)
- В **мультипоточных (multi-thread) программах** при работе с общей памятью без блокировок

Механизмы предотвращения во всех этих случаях очень похожи.

## Сценарий возникновения

Предположим, есть **две параллельные транзакции**, работающие с одними и теми же данными:

1. **T1** читает данные → получает значение
2. **T2** читает те же данные → получает то же значение
3. **T1** обрабатывает данные, применяет изменение → делает `UPDATE`
4. **T2** обрабатывает данные (на основе того, что прочитала изначально!) → делает `UPDATE`
5. Второй `UPDATE` от **T2** **перезаписывает (overwrite)** изменения T1

Изменение, сделанное первой транзакцией, **теряется** — отсюда название.

```
T1: R(x=10) → ... → U(x=20) → COMMIT
T2: R(x=10) → ... → U(x=20) → COMMIT   ← перезаписывает T1!

Результат в БД: x = 20  (ожидалось: x = 30)
```

## Конкретный пример с числами

Исходное значение: `x = 10`

| Шаг | T1 | T2 |
|-----|----|----|
| 1 | `READ x` → version 1, x = 10 | `READ x` → version 1, x = 10 |
| 2 | Хочу добавить +10 → x = 20 (version 2) | (пауза — scheduler приостановил) |
| 3 | `UPDATE x = 20` → `COMMIT` | — |
| 4 | — | Просыпается, хочет добавить +10 → x = 20 (думает, что там было 10) |
| 5 | — | `UPDATE x = 20` → `COMMIT` |

**Итог:** `x = 20`, хотя ожидалось `x = 30`

Обе транзакции хотели сделать `+10`. Но одна из десяток **потерялась**, потому что T2 перезаписала результат T1.

## Аналогия: запросы к серверу

То же самое происходит, когда клиент отправляет два параллельных запроса:

```
Клиент → сервер: +10  ┐
Клиент → сервер: +10  ┘  (параллельно)

Ожидание: x + 20
Реальность: x + 10  ← одно применилось, другое перетёрло его
```

## Аналогия: многопоточность

В мультипоточном программировании — та же семантика:

- Два потока читают общую переменную
- Оба изменяют её на основе прочитанного значения
- Один поток перезаписывает результат другого

**Решения в многопоточности:**
- **Locks (блокировки)** — запрещают параллельный доступ
- **Atomics** (например, атомарные операции в Redis) — защищают от Lost Update на уровне операции

В базах данных используются похожие, но специфичные механизмы (рассматриваются далее).
