# Missing or Double Read

## Что это такое?

**Missing Read** и **Double Read** — редкие аномалии чтения, которые могут возникать при параллельном выполнении транзакций в условиях низкого уровня изоляции.

- Встречаются не во всех базах данных
- Сложно воспроизвести намеренно
- Возникают только если **не используются блокировки** на уровне приложения или транзакции

## Контекст возникновения

Есть таблица со множеством строк. Транзакция выполняет `SELECT` с условием по нескольким строкам — например:

```sql
SELECT * FROM payments WHERE amount >= 1000;
```

Особенность такого запроса:
- База данных **не лочит всю таблицу** и **не лочит сразу все строки**
- Строки перебираются и читаются **по одной**
- Одновременно параллельные транзакции могут **изменять, добавлять или удалять** строки в этой же таблице

Если индекс — **B-tree**, при изменении значения строки может происходить **ребалансировка** дерева — узел перемещается на другую позицию в структуре.

## Double Read (двойное чтение)

### Сценарий

1. Транзакция T1 читает строки по одной: прочитала строки 1, 2, 3... остановилась на текущей
2. Параллельная транзакция T2 делает `UPDATE` одной из **уже прочитанных** строк
3. B-tree ребалансируется → узел перемещается **вперёд по индексу**, туда, где T1 ещё не была
4. T1 продолжает чтение и **встречает этот узел снова**

**Результат:** одна и та же строка прочитана **два раза**.

```
Позиции в B-tree: [1][2][3][4][5][6][7]
T1 прочитала:     [1][2][3] ← current

T2 меняет строку [2] → ребалансировка → [2] переезжает на позицию [6]

T1 продолжает:    [4][5][6←это снова строка 2!][7]
                              ^^^
                         Double Read
```

## Missing Read (пропущенное чтение)

### Сценарий

1. Транзакция T1 читает строки по одной: прочитала строки 1, 2, 3... остановилась на текущей
2. Параллельная транзакция T2 делает `UPDATE` строки, которую T1 **ещё не читала**
3. B-tree ребалансируется → узел перемещается **назад по индексу**, туда, где T1 **уже была**
4. T1 продолжает чтение и **никогда не встречает** этот узел

**Результат:** строка **вообще не попадает** в результат, хотя удовлетворяет условию `WHERE`.

```
Позиции в B-tree: [1][2][3][4][5][6][7]
T1 прочитала:     [1][2][3] ← current

T2 меняет строку [5] → ребалансировка → [5] переезжает на позицию [2]

T1 продолжает:    [4][6][7]
                     ↑
           строка [5] пропущена — Missing Read
```

## Почему БД не лочит весь индекс?

Блокировка всей B-tree структуры означала бы, по сути, **блокировку всей таблицы** — это крайне дорогая операция по производительности. Поэтому базы данных на низких уровнях изоляции этого не делают.

## Практическое значение

- Обе аномалии — **редкие и нечастые** случаи
- На практике, скорее всего, не будут замечены
- **Бизнес-логика приложения** должна быть построена так, чтобы нивелировать последствия подобных аномалий — даже если данные были прочитаны некорректно, это не должно критично влиять на результат
