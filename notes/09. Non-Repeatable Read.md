# Non-Repeatable Read (Неповторяемое чтение)

## Что такое Non-Repeatable Read?

**Non-Repeatable Read** (также называется **Read-Write конфликт**) — аномалия, при которой:

1. Транзакция читает какие-то данные
2. Другая транзакция **изменяет и коммитит** эти данные
3. Первая транзакция читает те же данные снова и получает **другое значение**

То есть в рамках **одной транзакции** одни и те же данные при повторном чтении возвращают разные результаты.

> **Неповторяемое чтение** — несколько раз читали, и результат каждый раз может быть разным, если кто-то параллельно обновил данные.

## Ключевое отличие от Dirty Read

| | Dirty Read | Non-Repeatable Read |
|---|---|---|
| Данные закоммичены? | **Нет** (временные) | **Да** (зафиксированы) |
| Валидно в PostgreSQL? | Нет (запрещено) | **Да** (на дефолтном уровне) |

- Если данные **не были закоммичены** — мы их не получим (Dirty Read исправлен)
- Если данные **были закоммичены** другой транзакцией — мы получим новое значение, и это **валидная ситуация** на дефолтном уровне PostgreSQL (`READ COMMITTED`)

## Схема

```
Транзакция 2         База данных          Транзакция 1
     |                    |                    |
     |--- читает: 10 ----->|                    |
     |                    |<--- читает: 10 -----|
     |                    |                    |
     |                    |<--- UPDATE до 20 ---|
     |                    |<--- COMMIT ---------|
     |                    |                    |
     |--- читает: 20 ----->|                    |
     |   (другое значение!)                    |
```

## Пример с конкретными значениями

| Шаг | Транзакция 2 | Транзакция 1 |
|-----|-------------|-------------|
| 1 | Читает: `10` (version 1) | Читает: `10` (version 1) |
| 2 | | Обновляет до `20` (version 2) |
| 3 | | `COMMIT` |
| 4 | Читает снова: получает `20` | |

**Итог:** Транзакция 2 в рамках одной сессии получила сначала `10`, затем `20` — **два разных значения**.

## Это валидно или нет?

На **дефолтном уровне PostgreSQL** (`READ COMMITTED`) — это **валидная ситуация**:
- Если данные были изменены и **закоммичены** — мы вправе их считать
- Если **коммита не было** — мы считать не можем (защита от Dirty Read)

Правило: **нет коммита → нельзя читать; коммит был → можно читать**.

## Когда это проблема?

Когда бизнес-логика рассчитывает на то, что данные, прочитанные в начале транзакции, **не изменятся** в ходе её выполнения. Транзакция может принять решение на основе `10`, а к моменту завершения значение уже `20`.
